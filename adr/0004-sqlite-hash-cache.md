# Хранение кэша хэшей в базе SQLite

## Контекст и постановка задачи

Повторный поиск по неизменённой папке должен выполняться не менее чем в два раза быстрее первого (REQ-PERF-003). Для этого приложение должно сохранять вычисленные хэши файлов с ключом (путь, размер, дата изменения) и позволять просматривать число записей и очищать кэш в настройках (REQ-FUNC-022). При повреждении кэша приложение должно пересоздать его без падения (REQ-REL-003).

## Драйверы решения

* Быстрый поиск записи по пути файла при повторном сканировании.
* Надёжное сохранение на диск без повреждения при прерывании.
* Поддержка просмотра количества записей и очистки кэша.

## Рассмотренные варианты

* База данных SQLite через модуль `QtSql`
* Бинарный файл кэша
* JSON-файл

## Итог решения

Выбранный вариант: «База данных SQLite через модуль `QtSql`», потому что SQLite обеспечивает индексированный поиск и транзакционность «из коробки».

### Последствия

* Хорошо, потому что быстрый поиск по индексу, не нужно загружать весь кэш в память.
* Хорошо, потому что транзакции защищают файл от частичной записи.
* Плохо, потому что добавляется зависимость от модуля `QtSql` и драйвера `qsqlite.dll` в портативной поставке, требуется создание и миграция схемы таблицы, а трудоёмкость реализации и тестирования оценивается в 4,0 чел.-дн.

### Подтверждение

Тест повторного поиска с замером времени и тест восстановления после порчи файла базы.

## Плюсы и минусы вариантов

### База данных SQLite

* Хорошо, потому что транзакции и индексы.
* Плохо, потому что лишняя зависимость в сборке и высокая трудоёмкость (4,0 чел.-дн.).

### Бинарный файл

* Хорошо, потому что не требует дополнительных модулей Qt и пишется проще.
* Плохо, потому что загружается в память целиком.

### JSON-файл

* Хорошо, потому что читаем человеком.
* Плохо, потому что медленно парсится и занимает много места при десятках тысяч записей.
