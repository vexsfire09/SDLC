# Хранение кэша хэшей в бинарном файле вместо SQLite

## Контекст и постановка задачи

В первом раунде согласования Заказчик попросил сократить сроки и стоимость проекта, при этом оставил кэш хэшей важным требованием для ускорения повторного поиска (REQ-FUNC-022, REQ-PERF-003). Предыдущее решение на базе SQLite (ADR-0004) оценивалось в 4,0 чел.-дн. и добавляло лишние библиотеки в портативную поставку. Требуется более простое и дешёвое в разработке решение.

## Драйверы решения

* Сокращение трудоёмкости реализации кэша с 4,0 до 2,5 чел.-дн.
* Отсутствие зависимости от `QtSql` и драйвера SQLite в портативной сборке (REQ-INST-001).
* Безопасное восстановление при повреждённом файле (REQ-REL-003).
* Умеренный объём памяти: до 100 000 записей (REQ-PERF-004).

## Рассмотренные варианты

* Бинарный файл `cache.bin` (запись и чтение через `QDataStream`, хранение в `QHash` в памяти во время поиска)
* База данных SQLite (ADR-0004)
* JSON-файл

## Итог решения

Выбранный вариант: «Бинарный файл `cache.bin` через `QDataStream`», потому что он не требует внешних модулей, быстро загружается и сохраняется, легко проверяется по заголовку «DVHC» и версии формата, и сокращает трудоёмкость на 1,5 чел.-дн.

### Последствия

* Хорошо, потому что нет зависимости от `QtSql`, меньше размер поставки, реализация и тестирование занимают 2,5 чел.-дн.
* Хорошо, потому что при несовпадении заголовка или ошибке чтения файл удаляется и создаётся заново (REQ-REL-003).
* Хорошо, потому что запись выполняется во временный файл `cache.bin.tmp` с последующим переименованием, чтобы избежать порчи при сбое.
* Плохо, потому что весь кэш загружается в память на время поиска (для 100 000 записей — около 15–20 МБ, что укладывается в лимит 500 МБ из REQ-PERF-004).

### Подтверждение

Замер ускорения повторного поиска (REQ-PERF-003), замер потребления ОЗУ (REQ-PERF-004) и тест запуска с испорченным `cache.bin` (REQ-REL-003).

## Плюсы и минусы вариантов

### Бинарный файл (QDataStream)

* Хорошо, потому что минимум кода, высокая скорость чтения/записи, нет новых зависимостей.
* Плохо, потому что нет выборочных запросов — файл читается целиком.

### SQLite (ADR-0004)

* Хорошо, потому что не держит весь кэш в памяти.
* Плохо, потому что лишняя зависимость и оценка 4,0 чел.-дн.

### JSON-файл

* Хорошо, потому что читаем человеком.
* Плохо, потому что занимает в 2–3 раза больше места и медленно парсится.

## Дополнительная информация
